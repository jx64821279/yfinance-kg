# 知识图谱 demo：数据质量改造与客户接入

---

## 概述

本项目是在仓库最早那一版的基础上往前走了一步。

（下文把最早那一版简称 **v1**，本文档描述的这一版简称 **v2**。）

**v1** 建立了 `事件 → 主题 → 概念 → 公司股票 → 基金（产品）` 这条链路，用公开市场数据（Yahoo Finance / SEC EDGAR / Google News）构建出 **436 条事件、626 节点 / 1358 边**的知识图谱，口径见 [yf_kg_data.md](yf_kg_data.md) 与 [yf_kg_architecture.md](yf_kg_architecture.md)。

**本版做了两件事。**

**一是处理新闻数据质量、重建知识图谱**：把新闻语料从"逐实体检索"改成"**宽流为主 + 分层过滤**"，事件从 436 条扩到 **1031 条**；资产类别从"几乎全是权益"变成**权益/大宗/固收三足**；图谱从 626 节点扩到 **1265 节点 / 1805 边**；并新增了 **scope 分层**和**检索层的第一块**。

**二是在图上接入客户**：以客户为对象、用知识层判断外部事件对他的影响，用 20 个合成客户（真实数据尚未拿到）打通"**一个客户 → 他的持仓与行为暴露在哪些主题下 → 对他意味着什么**"，产出 20 份客户简报，包含**暴露地图 / 需求缺口 / 时机与避雷 / 行动建议**。

## 1. 上一版留下的四个数据质量问题

上一版的四个具体毛病（都查过、有数字）：

| 问题 | 具体表现 |
|---|---|
| 检索式抓取 | 语料是"逐 ticker 搜索"来的，等于自己划好考纲，评估上有偏差 |
| 时效混乱 | 新闻跨度 2025-10 ~ 2026-09，差了近一年 |
| 重复与低质稿 | 同一事件多家转载（21 个近似重复簇）；大量"Sector Update / Premarket"模板行情稿 |
| 覆盖面窄 | **资产类别 83% 是 Equity**，宏观/政治事件几乎进不来 |

结论：不是"筛新闻"或"筛 LLM 产物"二选一，而是**输入端和产物端两层都要治**。

## 2. 新闻层改造（数据质量这部分的重点）

### 2.1 抓取：从"实体检索"改成"宽流为主"

| 通道 | 做法 | 条数 |
|---|---|---|
| **wide**（主） | Google News 宽检索 10 个类目词 × `when:30d` | 1000 |
| **topic**（增量） | BUSINESS / TECHNOLOGY 类目订阅 | 106 |
| **entity**（补充） | 逐 ticker 的 Yahoo 财经搜索 | 263 |
| 合计 | | **1369**（v1 是 627） |

**关键设计**：主通道**不含任何实体词**（用的是 `stock market`、`Federal Reserve`、`semiconductor`、`oil prices` 这类宽类目），这样才不会出现"用已知实体检索来的新闻，去证明系统能发现影响"。

实测：10 个检索词之间几乎不重复（980 条里只有 20 个标题重复），说明宽流确实在扩大覆盖面。

### 2.2 过滤：时间窗 + 相关性分级 + 去重

1. **时间窗**：以语料里最新日期为基准保留最近 30 天（不用"今天"，保证可复现）→ 剔除 35 条
2. **相关性**：只用**与新闻无关的外部先验**判定（公司名/品牌词/产品名/ticker + 产品定义词 + 人工宏观词表）→ 剔除 205 条完全不沾边 + 36 条"非 universe 的公司财报"
3. **去重**：标题精确去重（跨通道合并）49 条 + **同日**近似重复 4 条

结果：**1369 → 1040 条**

> 去重为什么加"同日"这个条件：v1 曾把不同日期的 `Sector Update: Tech Stocks …` 当成重复，那是误伤——它们是每日盘面播报，不是转载。

### 2.3 scope 分层（最有价值的新机制）

给每条新闻打一个**作用范围**标签，用它约束后面的抽取：

| scope | 判据（全部用不依赖新闻的先验） | 抽取时的约束 |
|---|---|---|
| `entity` | 命中 universe 公司/产品名 | 允许挂标的，但要有原文依据 |
| `sector` | 命中产品定义词（semiconductor、AI、gold、oil…） | 同上，谨慎 |
| `macro` | 命中宏观/政策词（Fed、inflation、tariff、OPEC…） | **禁止**挂个股 |
| `market` | 命中大盘综述词（stock market、S&P、Nasdaq…） | **禁止**挂个股 |
| `weak` | 来自实体通道但标题未命中 | 只允许有原文依据的标的 |
| `off` | 宽流里完全不沾边的 | 不抽取，丢弃 |

规则先粗分，再把"定不准的" 324 条交给 LLM **批量复核**（17 批）：

- market 桶里**剔除 35 条**（多为不在 universe 的公司财报，如 Snowflake、Macy's）
- **改判 12 条**
- 从"未命中桶"里**捞回 26 条**（说明纯规则漏了约 13%）

最终语料：**1031 条**

### 2.4 抽取：按 scope 施加约束 + 证据校验

- `macro` / `market` 两类共 274 条事件，**零违规**（一条都没挂个股）——v1 做不到这一点
- 要求模型输出 `evidence`（公司名 → 标题里的原文片段），脚本侧校验：**标题里找不到的名字直接丢弃**
- 实体解析分两层：公司走归一化索引（一家公司多个代码），产品走别名表（QQQ、SMH…）

结果：**1031/1031 抽取成功**；证据校验失败 0；146 条事件有原文依据的标的。

## 6. 两个设计决策

### 6.1 概念与主题只做知识层，不做推荐

- **KG 只存事实**：谁持有谁（带权重）、谁属于哪个概念、事件点名了谁、事件属于哪个主题
- **一阶/二阶打分不进图**：放在独立脚本 + 独立文件（`exposure_v2.py` / `exposure_v2.json`）
- 理由：分数是**策略输出**、参数会随业务调整；写进图会导致"改一个折扣系数就要重建整张图"
- 这也和 FinKario 原项目的思路一致：他们的 KG 是知识容器，RAG 两阶段检索在它之上跑

### 6.2 未上市的 AI 实验室（OpenAI / Anthropic）先不建节点

它们确实会影响我们的上市公司，路径有四条：

1. **供应链**：OpenAI 采购 NVDA / 台积电 / 三星的芯片（我们已抽到"Samsung to help fortify OpenAI's semiconductor supply chain"这条事件）
2. **并购**：ADI 收购 Alif Semiconductor（事件已正确落到 ADI）
3. **持股**：微软持 OpenAI、亚马逊与谷歌投 Anthropic，而 MSFT / AMZN / GOOGL 都在我们的 AI 与纳指概念里
4. **叙事**：它们是 AI 主题的核心，一条"暂停训练"就能压 AI 板块

**这次的取舍**：不建私有公司节点，先用"事件 → AI 主题 → AI 概念 → 产品"覆盖。实测那 11 条提到它们的新闻**全部通过 AI 概念走到了产品**。将来若要精确到"影响哪家上市公司"，再加 `PrivateCompany` 节点与 `INVESTED_BY` / `SUPPLY_CHAIN` 边即可。

## 7. 检索层：事件 → 产品曝光度

`exposure_v2.py`：输入一条事件 → 在 KG 上查两跳 → 输出**产品排序 + 可解释路径**。

这一层是知识层与客户层之间的接口：客户简报里的"暴露地图"就是用它算出的产品分数，再乘上客户的持仓权重得到的。

打分规则：

```
一阶（直接持有）：持仓权重 × 方向
二阶（同概念）：该产品在概念上的集中度 × 0.30 × 方向
```

实测两条：

| 事件 | 排序结果 |
|---|---|
| 一条点名英伟达的新闻 | QQQ +0.52 → AIQ +0.44 → XLK +0.23 → SMH +0.19 → SOXX +0.13 → BOTZ +0.06 |
| 一条加息新闻 | AGG −0.60 → TLT −0.60 → UUP −0.45 |

**意义**：以前一条 AI 新闻会"同等推给 6 只产品"，现在有了排序（QQQ 与 BOTZ 差近 10 倍）。

## 8. 踩过的坑

| 坑 | 现象 | 处理 |
|---|---|---|
| yfinance 库被风控 | `YFRateLimitError`，换版本、重试都无效；同一机器用 urllib 直连却返回 200 | 自建直连客户端（cookie + crumb） |
| `earnings` 一词两义 | 既是"公司财报"也是"个人收入"，导致教育/就业类新闻被当成市场新闻 | 从市场词表移除，改由 LLM 复核 |
| 单复数/缩写漏配 | `stock market` 匹配不到 `stock markets`；`A.I.` 匹配不到 `ai` | 词表匹配加复数容错 + 缩写归一 |
| 证据校验的两个 bug | `JD.com` 因标点归一不一致永远匹配不上；两字母代码（MU）被"长度≥3"跳过 | 两侧同口径归一 + 允许 2 字符 |
| 产品名误匹配 | 加密语境里的 "QQQ Token" 被当成 Invesco QQQ | 加加密语境拦截 |
| 事件域被模型自造 | 出现 `CommodityEvents` 等自定义值 | 收敛到 5 个受控值 |

## 9. 以客户为中心：用知识层判断影响

这个 demo 的目标一直是以**客户**为对象，借助知识层（KG）来生成对客户有用的东西：

```
一个客户
  → 他持有什么、最近在关心什么
  → 这些暴露落在知识图谱的哪些主题下（用 KG 判断新闻对他的影响）
  → 需求机会 / 互动时机 / 行动建议
```

具体要产出三类结果：**识别潜在客户需求与业务机会、判断更合适的客户互动时机、形成可供客户经理参考的行动建议**。

知识层在这个过程中承担"判断影响"这一环：新闻不直接落到客户身上，而是先经过 `事件 → 主题 → 概念 → 产品` 的传导，再用客户自己的持仓去接——**这一步就是"financial knowledge"起作用的地方**。

## 10. 客户数据：20 个合成客户

真实的客户交互数据、客户 360、储蓄与行为数据都还没拿到，所以先用**结构一致的合成数据**把链路跑通——以后真数据到位，字段对得上就能直接替换，下游代码不用改。

做成**一张 CSV、一行一个客户、23 列**，多值字段收进单元格（`;` 分隔条目、`|` 分隔条目内部字段）。规模：

| 内容 | 数量 |
|---|---|
| 客户 | 20 |
| 持仓条目 | 95 |
| 交易记录 | 111 |
| App 行为 / 客服咨询 | 49 |
| 客户经理交流 | 21 |
| 推荐的 offer | 20 |

客群覆盖六类：保守退休 / 稳健中产 / 平衡 / 科技进取 / 跨境偏好 / 高净值多元；风险等级 C1×1、C2×5、C3×6、C4×7、C5×1。

**内置的一致性规则（跑过校验）**：每个客户持仓权重合计 100；持仓市值合计 = 总资产 − 闲钱 − 定期存款；每一笔持仓都有对应的买入流水；状态为"已接受"的 offer 一定在持仓里；所有产品代码、概念名、资产类别都取自 KG——这一点是刻意的，**客户层一接进来就能和 事件 → 主题 → 概念 → 股票 → 基金 那条链咬合**。

## 11. 架构：知识层 / 客户层 / 决策层

```
新闻 / 事件
   ↓  知识层（共享，预建，就是这张 KG）
Event → Theme → Concept → Stock ← Fund(产品) → AssetClass
   ↓  客户层（私有，单独存，查询时按产品 join）
Customer 的持仓 / App 行为 / 咨询 / offer
   ↓  决策层（不进图，纯计算）
暴露地图 × 需求缺口 × 时机与避雷 → 行动建议
```

**关键取舍：客户不进图。** 四条理由——规模不同（知识层千级共享，客户层是私有且会持续增长）、隐私不同（不能跨客户泄漏）、更新频率不同（持仓每天变，知识层慢慢长）、检索方式不同（知识层要语义检索，客户层是条件明确的过滤和聚合）。所以两边用**产品**做接口，查询时 join。

作为对照：FinKario 原论文并**没有客户层**，它的终点是股票趋势预测；而且它用的也不是图数据库，是 LightRAG（图存 NetworkX、向量存 nano-vectordb）。本项目保留的是它"**事件增强的知识图谱 + 按需拼子图 + 用证据生成理由**"这个思路，客户侧换成关系表。

## 12. 客户简报是怎么算出来的

每份简报四块，前三块是**确定性计算**（可复算、可审计），只有最后一块交给模型：

| 块 | 怎么算的 |
|---|---|
| **暴露地图** | 事件 → 产品的曝光分 × 客户在该产品上的持仓权重 × 事件的实质性权重，再按主题聚合；每个主题附 `drivers`（是哪些持仓让它变正/变负） |
| **需求缺口** | 客户 App 行为里关注/咨询过的概念或资产类别，持仓里没有覆盖到的 |
| **时机与避雷** | 定期到期、闲钱占比、最近是否刚联系过（冷却期）、之前有没有拒过同类产品 |
| **行动建议** | 把上面三块的事实交给 LLM 写成客户经理能直接用的话 |

"实质性权重"是为了压掉泛泛的模板行情稿：按事件类别（公司/大宗 1.0、政策 0.9、宏观 0.8、大盘 0.6）乘范围权重（entity 1.0 → weak 0.6）。

## 13. 三处口径调整

下面三处都是把数跑出来、看结果才发现不合理的，记录于此：

| 问题 | 现象 | 改法 |
|---|---|---|
| 实质性权重过狠 | 大盘类权重只有 0.3×0.4=0.12，把 C014（100% 权益客户）最要命的"股市回调与崩盘风险"压到看不见（净 −0.87） | 权重区间收窄，最低档变成 0.6×0.7=0.42；该主题恢复到 −2.81，回到她的风险主题第一名 |
| 主题强度被条数堆量 | C009 的"美联储货币政策"131 条事件堆出 −12，但覆盖天数只有 26 天 | 同时给出**覆盖天数**和**每条均值**，排序口径做成开关（`net` 总量 / `damp` 阻尼 / `avg` 均值），默认 `net` |
| 到期天数假精确 | 数据里到期只到"月"（2026-10），按月初算天数得出"剩余 2 天" | 改成按月表述："2026-10 到期（下个月到期；数据只到月份，无具体日期）" |

还有一处是**打分规则本身的错**，见下一节。

20 份简报一共出现 **17 个主题、4 个需求缺口**。可以看出：越保守、债券越重的客户，暴露越集中在利率主题上；越年轻的权益客户，暴露越集中在回调风险和 AI 主题上——这个分化本身说明口径是有效的。

## 15. LLM 建议的质量检查

让 DeepSeek 基于结构化简报写 3~5 条建议（引用具体数字、风险机会分开、守住风险等级）。**表现较好的地方**：会引用客户经理的交流记录（"客户在 9/5 面访明确表示厌恶股市波动"）、能识别冷却期（"9/24 刚联系过，距今 5 天，不宜重复触达"）、不硬推被拒产品（"UUP 已被拒绝，需换角度"）。

**发现并修掉的三个问题：**

| 问题 | 表现 | 根因与修法 | 验证 |
|---|---|---|---|
| 产品越界 | C003 没持有 AIQ、缺口候选也是空的，建议里却写"可提 AIQ" | prompt 里带了**完整的 13 只产品风险表**，模型顺手拿来用。改成只传"该客户持仓 + 候选 + 被拒"三组，并加硬约束 | 扫 20 份建议里出现的产品代码，**0/20 越界** |
| 到期假精确 | 见 §13 | 按月表述 | 已核 |
| 主题硬凑 | C013 写"石油与能源市场净 +0.53，且客户 GLD 持仓 20%" | 分两层：**prompt 侧**给每个主题加 `drivers`；**数据侧**查下去发现真凶是 exposure 的规则 E——"资产型概念辐射同资产类别的产品"一律给 0.5 折扣，而"黄金"和"原油"同属 Commodity，于是油价新闻会给黄金基金打分（GLD 有 **248 条**暴露来自这条路） | 规则 E 改成按资产类别设权重：**债券保留 0.5**（AGG 和 TLT 确实同受利率驱动），**商品/外汇取消**；修正后 GLD 不再从油价主题拿到任何非零分 |

最后一条值得特别注意：**是 LLM 的输出反过来暴露了数据侧的问题**。光看打分表看不出来"油价给黄金打分"有什么不对，但让模型把它翻译成人话，问题立刻显形。

## 16. 关于 embedding 的决策

**论文的做法与本版的选择。** FinKario 原版用 `text-embedding-3-small`（OpenAI），把图谱向量化之后做两阶段检索。本版**没有引入向量检索**，因为 DeepSeek 不提供 embedding 接口（实测 `POST /v1/embeddings` 返回 404），要用就得额外接入一个 embedding 服务或本地模型。

**为什么这条链路上用不上。**

1. 文本 → 图节点的语义匹配，**已经在建图阶段由 LLM 完成**（原始主题归并、主题→概念映射都是调模型做的），查询阶段再用向量等于把同一件事重做一遍
2. 客户侧是**精确匹配**：客户 → 持仓 → 产品走的是代码和权重，没有模糊语义需要处理
3. 规模只有 1265 个实体，向量检索的相对优势体现不出来

**可选方案已经验证过。** 若后续需要，本地方案是可行的：`fastembed` + onnxruntime，模型用 `jinaai/jina-embeddings-v2-base-zh`（0.64 GB、768 维、中英混合），本地缓存，离线加载 1.4 秒；用 KG 里的实体名做了一组检索测试，top-3 全部命中。

**什么时候真正需要。** 出现以下任一需求时再引入：

- 客户经理用自然语言提问（查询锚点不确定）
- LLM 抽取失败时，需要语义兜底召回
- 图谱规模增长到几万节点以上

**结论**：本版链路不依赖向量检索；检索层与知识层在设计上是分开的，后续需要时接入，不影响现有管线。

## 17. 尚未完成与已知限制

- **公司业务描述没补**（Yahoo 限流时没跑完）：概念成员目前仍只来自 ETF 前十大持仓
- **每只产品只有前十大持仓**（80 条持仓边），这是"事件 → 产品"覆盖的主要瓶颈，不是宇宙大小
- 主题词表还有 4 个未映射（确实无对应产品）
- 私有公司（OpenAI / Anthropic 等）未建模
- 一阶/二阶的权重参数还没调优（目前同概念折扣 0.30；且跨概念会累加，例如债券类新闻 AGG 会拿到 0.6）
- **客户数据是合成的**：真实数据（客户交互 / 360 / 储蓄与行为）还没拿到，字段对齐后可直接替换
- **风险等级下限表是按现有客户持仓倒推的**，真实业务里应该由合规口径给
- 客户简报里的"时机"只有定期到期、闲钱、冷却期、被拒记录四类信号，没有考虑触达渠道偏好和客户活跃度
- **推荐层还没做**：现在产出的是分析（暴露在哪、缺口在哪），还不是动作。推荐层要给出推哪只产品、建议金额与占比，过风险等级与集中度约束，排出客户经理当天该先联系谁，输出成行动清单，并用 offer 的接受/拒绝结果回流调整下一次推荐
- **RAG 层还没做**：现在的建议只看得到汇总数字，看不到原文。补上之后能引用具体新闻（标题 / 日期 / 来源）、每条结论可追溯，也支持客户经理追问"依据是什么"
- "学习 news → customers 的传导路径"需要真实数据里的事件-行为时间对齐才能做
