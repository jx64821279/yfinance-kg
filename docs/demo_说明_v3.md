# 知识图谱 demo v3：主题层重构与检索 / 决策层

> 本文档对应 **v3**。v2（数据质量改造 + 客户接入）见 [demo_说明.md](demo_说明.md)；v1 的口径见 [yf_kg_data.md](yf_kg_data.md) 与 [yf_kg_architecture.md](yf_kg_architecture.md)。
>
> 注意：`_yf_data/subs/` 是检索层的中间产物（20 份客户子图，约 9.6 MB），**不在仓库里**，按本文最后一节的命令一条就能重新生成。

---

## 概述

v2 建立了「新闻 → 知识图谱 → 产品 → 客户简报」这条链。v3 在它之上做了三件事：

**一是重构主题层**：主题从"LLM 自由抽取 + 归并成 41 个规范主题"改成「**概念 × 驱动**」的组合，不再维护主题名词表，一条事件可以落到多个概念上。

**二是把图谱装进数据库、补上检索层**：KG 和客户数据进 SQLite，新增"取客户子图"这一步（有界选取），客户简报改为从子图取数。

**三是补上价格与决策层**：加入 13 只 ETF 的日线收盘价（持仓近一周表现），并把子图 + 事实清单交给模型，产出可执行、带证据引用的决策。

（下文把上一版简称 v2，本版简称 v3。）

## 1. v2 主题层的三个毛病

| 毛病 | 具体表现 |
|---|---|
| 归并要反复调模型 | 1031 条事件抽出的主题是自由文本（**919 个**），要 LLM 归并成 41 个规范主题，还要人工补丁去补漏归的 |
| 一维稀疏清单 | 41 个主题里，「美联储货币政策」占 174 条，而**有 7 个主题各只有 1 条**；遇到清单里没有的只能强行归类 |
| 驱动和落点混在一个标签里 | 「美联储货币政策」其实是个**驱动**，它把落点（债券 / 美元 / 权益）藏在"主题 → 概念"的映射后面；一条事件只能挂一个主题 |

## 2. 改动一：主题层改成「概念 × 驱动」

### 2.1 两个封闭集合相乘

```
概念（12 个，由产品反推，产品层互斥） × 驱动（11 个，沿用 driver_category 框架）
```

每条事件标两件事：**概念 0~3 个**（按相关性排序，宁缺毋滥，落不到就空）+ **驱动 1 个**。主题是组合的产物，**不再维护名词表**，新的组合自动就是一个新主题。

用到的组合：**86 / 132**（12 × 11 的空间）。

### 2.2 标注结果

| 维度 | 分布 |
|---|---|
| 每条事件的概念个数 | 0 个 **161**｜1 个 **457**｜2 个 **197**｜3 个 **216** |
| 驱动 | 市场资金面 307、宏观与汇率 244、政策监管 101、地缘政治 100、技术创新 78、战略动作 63、供给 45、收入 38、需求 30、行业周期 18、效率成本 7 |
| 概念被引用次数 | 纳斯达克100 220、半导体 180、人工智能 175、美国长期国债 171、美国综合债券 169、原油 140、美国科技 106、黄金 102、美元指数 82、中概互联网 76、中国科技 76、**机器人与自动化 2** |

### 2.3 通道机制：落不到概念的事件怎么处理

严格标注会产出一批"没有落点"的事件。直接用会丢信息，硬塞又会污染概念桶，所以按驱动分流：

| 通道 | 判定 | 处理 |
|---|---|---|
| **concept** | 有落点概念 | 正常参与暴露计算，**870 条（84%）** |
| **market** | 无概念，且驱动是「市场资金面 / 宏观与汇率」 | **市场层面**通道：不落具体产品，在简报里单独汇总成"大盘 / 情绪"一条，**59 条（6%）** |
| **gap** | 无概念，驱动是其余九类 | **无落点**通道：真正跟产品货架无关，**102 条（10%）** |

这条口径的意义：一条"周一看盘要点"不该算作影响纳斯达克概念（v2 就是这么落的，导致每个权益客户的简报都被这类稿子主导）；但它作为"大盘情绪"又确实该让客户经理看到。两条通道把它拆开了。

## 3. 改动二：图谱入库 + 检索层

### 3.1 为什么是 SQLite，不是图数据库

这一步要做的是"按关系筛选和聚合"（某客户持有什么、某事件影响哪些产品、某概念的敞口落在哪些客户），不是最短路、社区发现那类图算法。SQLite 单文件、免安装、可直接用工具打开；表结构是标准的节点表 + 边表，将来要换 Neo4j 只需改连接层。

顺带对照：**FinKario 原项目并没有数据库**——它用 LightRAG 的默认存储（图存 GraphML、向量存 nano-vectordb、其余存 JSON），而且是**按周切成互不相通的快照**（每周一个工作目录，文件存在就跳过）。我们这张图是累积的，所以放在库里查更合适。

### 3.2 库里的表

```
知识层：node / edge（含 6 个查询视图）+ event_fund_score（事件→产品曝光度）
客户层：customer / customer_holding / customer_behavior
        customer_advisor / customer_offer / customer_trade
价格：  price（ticker, date, close, adj_close, volume）
元信息：meta（来源文件、构建时间、各类行数）
```

库规模：**1.98 MB**，节点 1316 / 边 2590 / 曝光度 3654 条 / 价格 130 行 / 客户 20。

### 3.3 检索层：取一个客户的子图

`kg_subgraph.py` 从库里取出"与这个客户相关的一小片"，包含：

| 内容 | 说明 |
|---|---|
| 客户 + 持仓（含每只产品所属概念） | 画像是简报的基础 |
| **曝光明细** | 事件 × 他持有的产品 × 分数，决策层据此排序与聚合 |
| 缺口 | 关注过但持仓没覆盖到的概念 / 资产类别 |
| **市场层面事件** | 没有产品分数，但落在资产类别上，C 方案那条通道要用 |
| 行为 / 客户经理交流 / offer | 时机信号（冷却期、被拒过的产品） |
| 概念切片 | 候选产品要用（概念成员、锚定基金、产品持仓、全部 13 只产品） |
| 价格窗口 | 持仓近一周表现 |

### 3.4 有界选取：细粒度检索的"k"

不做截断的话，一个客户能拉出上万行曝光明细（宽基产品几乎什么都沾）。所以检索层做两步收口：

```
候选 21267 行（20 个客户合计）
   → 按「分数 × 持仓权重 × 实质性权重」排序，每个概念取 top-k
   → 每份平均选中 18.9 条（最少 11、最多 29），去重后 16.7 条
   → 20 份合计 378 条
```

选取策略默认 **balanced（正负两头各取一半）**，这一点很关键：

```
【半导体】  balanced： +0.077 战略动作   +0.077 收入   -0.077 收入
           strength： +0.077 战略动作   +0.077 收入   +0.077 收入
```

只按强度取，会把负向信号整个丢掉，模型看到的就是一片利好。参数：`--top-events`（每概念几条）、`--top-market`（市场层面几条）、`--pick`（策略）、`--max-events`（总数上限）。

### 3.5 与 FinKario 两阶段检索的对应

| 阶段 | FinKario | 本项目 |
|---|---|---|
| 粗粒度锚定 | 向量匹配「股票 + 日期」 | 外键：客户 → 持仓 → 产品 → 概念 |
| 细粒度扩展 + k | 检索周边实体，取 k 个 | 每个概念 top-k 事件 + 市场层面 top-k + 总数上限 |
| 映射回图 | `Mapping(·)`：向量 → 图节点（必须做） | 不需要（取出来的本来就是库里的行） |
| 交给模型 | 子图 + 查询 → 结论 | 决策层（见第 6 节） |

## 4. 改动三：简报改从子图取数，归桶从产品出发

### 4.1 为什么要改归桶口径

v3 里多概念事件的"主题"是拼接串（`美国长期国债 × 宏观与汇率、美国综合债券 × …`），**不同事件的组合和顺序都不一样**，按主题名归桶会把同一个概念拆成好几行：

```
美国长期国债 × 宏观与汇率、美国综合债券 × …   事件 22条
美国长期国债 × 宏观与汇率、美国综合债券 × …   事件 28条
美国长期国债 × 宏观与汇率、美国综合债券 × …   事件 20条
```

改成**从产品出发**：每只产品的暴露归入**它自己所属的那个概念**。因为「产品 → 概念」是一对一，每笔暴露只进一个桶，既不重复计数（一个事件可以落多个概念），也不会被打散。驱动（driver_category）作为二级展开保留。

改完之后 C009 的债券暴露就是干净的两条腿：

```
美国综合债券   净 -9.02   151条   持仓驱动 AGG -9.02   事件驱动：宏观与汇率 -8.39、市场资金面 -0.29
美国长期国债   净 -7.15   151条   持仓驱动 TLT -7.15   事件驱动：宏观与汇率 -6.55、市场资金面 -0.33
```

### 4.2 两条取数路径的等价性

简报保留两种取数方式：直接读文件（旧路径）/ 走子图（新路径）。**20 份简报逐项比对（概念暴露、市场层面、需求缺口、时机信号、组合表现、个券表现），0 处不一致。**

## 5. 改动四：价格 + 持仓近一周表现

### 5.1 两个口径要点

**时间锚点**：整条链锚在 `ref_date`（数据里最新的一天，2026-09-29）。所以价格要取"**截至 ref_date 的那一周**"，而不是"今天起的前一周"——否则拿到的价格和新闻窗口对不上，做决策就是错的。因此抓取时用 chart 接口指定日期区间，再截到 as_of 为止。

**复权价**：算涨跌幅必须用复权价，否则除权日会假跌。这 13 只 ETF 全在美股市场，交易日历统一，不需要处理跨市场假期。

### 5.2 结果

13 只 ETF × 最近 5 个交易日（另存 10 天备用），进入 `price` 表。

| | 近一周 |
|---|---|
| 跌得最多的产品 | TLT −4.31%、GLD −4.29%、CQQQ −5.95%、KWEB −3.94% |
| 逆势上涨 | UUP +0.95% |
| **20 个客户的组合** | **−3.79% ~ −1.17%（中位 −2.24%）** |

全部为负，和那个窗口里"利率上行 + 避险资产回调"的整体环境吻合。

### 5.3 前瞻与后验的对照才是价值所在

| 客户持仓 | 事件面（前瞻） | 价格面（后验） | 读法 |
|---|---|---|---|
| TLT | −7.15 | **−4.31%** | **一致**——"加息预期 → 长债跌"这条传导真实发生了 |
| SMH | +3.88 | **−0.09%** | **背离**——客户经理该追问：是传导还没到价格，还是这批"利好"本来就不强 |

## 6. 改动五：决策层

### 6.1 为什么单独一步

简报是**确定性的事实清单**（可复算可审计），决策是**模型的判断**。两者分开，出了问题才能分辨是"数字错了"还是"判断偏了"。所以决策层是独立脚本，输入是子图（含代表事件）+ 简报（汇总事实），输出是严格 JSON：

```json
{"priority": "高|中|低", "summary": "一句话结论",
 "risks":         [{"point": "…", "evidence": ["event_806", "event_335"]}],
 "opportunities": [{"point": "…", "evidence": ["event_718"]}],
 "actions":       [{"action": "…", "timing": "…", "reason": "…", "evidence": ["event_806"]}]}
```

提示词里的硬约束：只能提及允许范围内的产品；证据只能用给定的事件 id；价格是后验、事件面是前瞻，不能混；市场层面只作背景；被拒过的产品只能以"可换角度再谈"的方式提及；到期只精确到月。

### 6.2 自检：不信任模型的输出

每次生成后自动检查两件事：**引用的 event_id 是否在给定集合内**、**是否提到了 13 只产品之外的标的**。第一次跑 20 份时自检报了 1 处"越界"，查下来是**自检自己的误报**（把货币代码 `CNY` 当成产品），改成只在已知的 13 只产品货架内查越界后就干净了。另外加了 `--recheck`，不调模型就能用现有产物重跑自检。

### 6.3 质量验证

**20/20 生成成功，0 失败，自检 20/20 通过。** 抽查结果：

1. **证据指向正确**——把每条结论引用的事件回溯到它在子图里属于哪个概念，全部对得上：

```
[风险] 债券 / 久期风险    ← event_806（美国长期国债）、event_335（美国综合债券）
[风险] 黄金短期承压       ← event_022（黄金）
[机会] 半导体偏正        ← event_718（半导体）、event_471（纳斯达克100 / 半导体）
[背景] 市场情绪偏负       ← event_826（市场层面）
```

2. **冷却期守住了**——C003 在 9/24 刚电话联系过（距今 5 天），决策给出的第一条行动是"**暂不主动联系客户**"，时机写"冷却期内，最近一次电话沟通后仅 5 天"。

3. **被拒产品不硬推**——C018 拒过 CQQQ，决策明确写"不直接重复推荐被拒的 CQQQ"，改用她已有的 KWEB 做切入；C009 的 UUP 只在"曾被拒、可换角度"的语境里出现。

4. **两个维度没混**——结论写法是"固定收益暴露事件面偏负**且近一周回撤明显**"，前瞻和后验分开表述。

### 6.4 已知局限

优先级分布是 **18 高 / 2 中**。因为每个客户是**独立判断**的，这个"高 / 中 / 低"**没有横向可比性**——客户经理没法照着"18 个高优先级"去行动。要解决得做多客户统一排序，属于下一步的事。

## 7. 图谱 v3 与验证

| | v2 | **v3** |
|---|---|---|
| 事件 | 1031 | 1031（同一批语料） |
| 节点 / 边 | 1265 / 1805 | **1316 / 2590** |
| 主题 | 45（41 规范 + 4 兜底） | **96**（86 个「概念 × 驱动」+ 2 市场层面 + 8 无落点） |
| `HAS_THEME` 边 | 1031（一条事件一个主题） | **1660**（多落点事件会连多个主题） |
| `MAPS_TO` 边 | 62（一对多映射） | **86**（每个主题恰好对一个概念） |
| `BELONGS_TO` 边 | 41 | **96**（每个主题恰好对一个驱动） |
| 事件能落到产品 | 1006 / 1031（98%） | **870 / 1031（84%）** |

覆盖率下降是**预期结果**，不是退化：v2 把大盘 / 情绪类稿件也硬落到了"纳斯达克概念"上，v3 把它们分流到市场层面（59 条）和无落点（102 条）两条通道。前者在简报里单独汇总，后者本来就是"产品货架缺口"的证据。

**一个反复出现的数据发现**：机器人概念只有 2 条事件——新闻里几乎没有它的锚点，BOTZ 现在只能靠"人工智能"概念蹭到曝光。这是产品货架的**新闻缺口**，和"没有任何主题指向机器人"是同一个问题。

## 8. 尚未完成与已知限制

- **推荐层还没做**：从缺口到具体动作（推哪只产品、建议金额、集中度约束）、多客户优先级排序、行动清单、offer 结果回流
- **优先级没有横向可比性**（见 6.4），需要多客户统一排序
- **覆盖率 84%**：市场层面与无落点两条通道不进产品计算
- **机器人概念只有 2 条事件**：新闻锚点缺口
- **ETF 只有前十大持仓**（80 条持仓边），这是"事件 → 产品"覆盖的主要瓶颈，需要完整持仓数据
- **客户数据是合成的**（20 个客户）；**风险等级下限表是按现有持仓倒推的**，真实业务里应由合规口径给出
- **v2 的主题词表链路**（`build_theme_vocab.py` / `apply_theme_fixes.py` / `build_theme_concept_map.py`）在 v3 已不再使用，代码与产物仍在
