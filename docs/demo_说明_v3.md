# 知识图谱 demo v3：主题层重构与检索 / 决策层

---

## 概述

v2 建立了「新闻 → 知识图谱 → 产品 → 客户简报」这条链。v3 在它之上做了三件事：

**一是重构主题层**：主题从"LLM 自由抽取 + 归并成 41 个规范主题"改成「**概念 × 驱动**」的组合，不再维护主题名词表，一条事件可以落到多个概念上。

**二是把图谱装进数据库、补上检索层**：KG 和客户数据进 SQLite，新增"取客户子图"这一步（有界选取），客户简报改为从子图取数。

**三是补上价格与决策层**：加入 13 只 ETF 的日线收盘价（持仓近一周表现），并把子图 + 事实清单交给模型，产出可执行、带证据引用的决策。

**四是修了三处地基问题**：事件 id 从位置序号改成链接哈希、曝光度不再入库改成按需现算、修掉一阶直接暴露的索引 bug（见第 9 节）。

（下文把上一版简称 v2，本版简称 v3。）

## 1. v2 主题层的三个毛病

| 毛病 | 具体表现 |
|---|---|
| 归并要反复调模型 | 1031 条事件抽出的主题是自由文本（**919 个**），要 LLM 归并成 41 个规范主题，还要人工补丁去补漏归的 |
| 一维稀疏清单 | 41 个主题里，「美联储货币政策」占 174 条，而**有 7 个主题各只有 1 条**；遇到清单里没有的只能强行归类 |
| 驱动和落点混在一个标签里 | 「美联储货币政策」其实是个**驱动**，它把落点（债券 / 美元 / 权益）藏在"主题 → 概念"的映射后面；一条事件只能挂一个主题 |

## 2. 改动一：主题层改成「概念 × 驱动」

### 2.1 两个封闭集合相乘

```
概念（12 个，由产品反推，产品层互斥） × 驱动（11 个，沿用 driver_category 框架）
```

每条事件标两件事：**概念 0~3 个**（按相关性排序，宁缺毋滥，落不到就空）+ **驱动 1 个**。主题是组合的产物，**不再维护名词表**，新的组合自动就是一个新主题。

用到的组合：**86 / 132**（12 × 11 的空间）。

### 2.2 标注结果

| 维度 | 分布 |
|---|---|
| 每条事件的概念个数 | 0 个 **161**｜1 个 **457**｜2 个 **197**｜3 个 **216** |
| 驱动 | 市场资金面 307、宏观与汇率 244、政策监管 101、地缘政治 100、技术创新 78、战略动作 63、供给 45、收入 38、需求 30、行业周期 18、效率成本 7 |
| 概念被引用次数 | 纳斯达克100 220、半导体 180、人工智能 175、美国长期国债 171、美国综合债券 169、原油 140、美国科技 106、黄金 102、美元指数 82、中概互联网 76、中国科技 76、**机器人与自动化 2** |

### 2.3 通道机制：落不到概念的事件怎么处理

严格标注会产出一批"没有落点"的事件。直接用会丢信息，硬塞又会污染概念桶，所以按驱动分流：

| 通道 | 判定 | 处理 |
|---|---|---|
| **concept** | 有落点概念 | 正常参与暴露计算，**870 条（84%）** |
| **market** | 无概念，且驱动是「市场资金面 / 宏观与汇率」 | **市场层面**通道：不落具体产品，在简报里单独汇总成"大盘 / 情绪"一条，**59 条（6%）** |
| **gap** | 无概念，驱动是其余九类 | **无落点**通道：真正跟产品货架无关，**102 条（10%）** |

这条口径的意义：一条"周一看盘要点"不该算作影响纳斯达克概念（v2 就是这么落的，导致每个权益客户的简报都被这类稿子主导）；但它作为"大盘情绪"又确实该让客户经理看到。两条通道把它拆开了。

## 3. 改动二：图谱入库 + 检索层

### 3.1 为什么是 SQLite，不是图数据库

这一步要做的是"按关系筛选和聚合"（某客户持有什么、某事件影响哪些产品、某概念的敞口落在哪些客户），不是最短路、社区发现那类图算法。SQLite 单文件、免安装、可直接用工具打开；表结构是标准的节点表 + 边表，将来要换 Neo4j 只需改连接层。

顺带对照：**FinKario 原项目并没有数据库**——它用 LightRAG 的默认存储（图存 GraphML、向量存 nano-vectordb、其余存 JSON），而且是**按周切成互不相通的快照**（每周一个工作目录，文件存在就跳过）。我们这张图是累积的，所以放在库里查更合适。

### 3.2 库里的表

```
知识层：node / edge（含 6 个查询视图）
客户层：customer / customer_holding / customer_behavior
        customer_advisor / customer_offer / customer_trade
价格：  price（ticker, date, close, adj_close, volume）
元信息：meta（来源文件、构建时间、各类行数）
```

库规模：**2.11 MB**，节点 1316 / 边 2590 / 价格 130 行 / 客户 20。

**曝光度不入库**（见第 9 节）：它是策略输出，系数一调就要全量重算，存一份在库里迟早和图里的持仓权重对不上。检索层用到时现算。

### 3.3 检索层：取一个客户的子图

`kg_subgraph.py` 从库里取出"与这个客户相关的一小片"，包含：

| 内容 | 说明 |
|---|---|
| 客户 + 持仓（含每只产品所属概念） | 画像是简报的基础 |
| **曝光明细** | 事件 × 他持有的产品 × 分数（现算，只算他持有的那几只），决策层据此排序与聚合 |
| 缺口 | 关注过但持仓没覆盖到的概念 / 资产类别 |
| **市场层面事件** | 没有产品分数，但落在资产类别上，C 方案那条通道要用 |
| 行为 / 客户经理交流摘要 / offer | 时机信号（冷却期、被拒过的产品） |
| 概念切片 | 候选产品要用（概念成员、锚定基金、产品持仓、全部 13 只产品） |
| 价格窗口 | 持仓近一周表现 |

### 3.4 有界选取：细粒度检索的"k"

不做截断的话，一个客户能拉出上万行曝光明细（宽基产品几乎什么都沾）。所以检索层做两步收口：

```
候选 21267 行（20 个客户合计）
   → 按「分数 × 持仓权重 × 实质性权重」排序，每个概念取 top-k
   → 每份平均选中 18.9 条（最少 11、最多 29），去重后 16.6 条
   → 20 份合计 378 条
```

选取策略默认 **balanced（正负两头各取一半）**，这一点很关键：

```
【半导体】  balanced： +0.077 战略动作   +0.077 收入   -0.077 收入
           strength： +0.077 战略动作   +0.077 收入   +0.077 收入
```

只按强度取，会把负向信号整个丢掉，模型看到的就是一片利好。参数：`--top-events`（每概念几条）、`--top-market`（市场层面几条）、`--pick`（策略）、`--max-events`（总数上限）。

### 3.5 与 FinKario 两阶段检索的对应

| 阶段 | FinKario | 本项目 |
|---|---|---|
| 粗粒度锚定 | 向量匹配「股票 + 日期」 | 外键：客户 → 持仓 → 产品 → 概念 |
| 细粒度扩展 + k | 检索周边实体，取 k 个 | 每个概念 top-k 事件 + 市场层面 top-k + 总数上限 |
| 映射回图 | `Mapping(·)`：向量 → 图节点（必须做） | 不需要（取出来的本来就是库里的行） |
| 交给模型 | 子图 + 查询 → 结论 | 决策层（见第 6 节） |

## 4. 改动三：简报改从子图取数，归桶从产品出发

### 4.1 为什么要改归桶口径

v3 里多概念事件的"主题"是拼接串（`美国长期国债 × 宏观与汇率、美国综合债券 × …`），**不同事件的组合和顺序都不一样**，按主题名归桶会把同一个概念拆成好几行：

```
美国长期国债 × 宏观与汇率、美国综合债券 × …   事件 22条
美国长期国债 × 宏观与汇率、美国综合债券 × …   事件 28条
美国长期国债 × 宏观与汇率、美国综合债券 × …   事件 20条
```

改成**从产品出发**：每只产品的暴露归入**它自己所属的那个概念**。因为「产品 → 概念」是一对一，每笔暴露只进一个桶，既不重复计数（一个事件可以落多个概念），也不会被打散。驱动（driver_category）作为二级展开保留。

改完之后 C009 的债券暴露就是干净的两条腿：

```
美国综合债券   净 -9.02   151条   持仓驱动 AGG -9.02   事件驱动：宏观与汇率 -8.39、市场资金面 -0.29
美国长期国债   净 -7.15   151条   持仓驱动 TLT -7.15   事件驱动：宏观与汇率 -6.55、市场资金面 -0.33
```

### 4.2 两条取数路径的等价性

简报保留两种取数方式：直接读文件（旧路径）/ 走子图（新路径）。**20 份简报逐项比对（概念暴露、市场层面、需求缺口、时机信号、组合表现、个券表现），0 处不一致。**

## 5. 改动四：价格 + 持仓近一周表现

### 5.1 两个口径要点

**时间锚点**：整条链锚在 `ref_date`（数据里最新的一天，2026-09-29）。所以价格要取"**截至 ref_date 的那一周**"，而不是"今天起的前一周"——否则拿到的价格和新闻窗口对不上，做决策就是错的。因此抓取时用 chart 接口指定日期区间，再截到 as_of 为止。

**复权价**：算涨跌幅必须用复权价，否则除权日会假跌。这 13 只 ETF 全在美股市场，交易日历统一，不需要处理跨市场假期。

### 5.2 结果

13 只 ETF × 最近 5 个交易日（另存 10 天备用），进入 `price` 表。

| | 近一周 |
|---|---|
| 跌得最多的产品 | TLT −4.31%、GLD −4.29%、CQQQ −5.95%、KWEB −3.94% |
| 逆势上涨 | UUP +0.95% |
| **20 个客户的组合** | **−3.79% ~ −1.17%（中位 −2.24%）** |

全部为负，和那个窗口里"利率上行 + 避险资产回调"的整体环境吻合。

### 5.3 前瞻与后验的对照才是价值所在

| 客户持仓 | 事件面（前瞻） | 价格面（后验） | 读法 |
|---|---|---|---|
| TLT | −7.15 | **−4.31%** | **一致**——"加息预期 → 长债跌"这条传导真实发生了 |
| SMH | +4.24 | **−0.09%** | **背离**——客户经理该追问：是传导还没到价格，还是这批"利好"本来就不强 |

## 6. 改动五：决策层

### 6.1 为什么单独一步

简报是**确定性的事实清单**（可复算可审计），决策是**模型的判断**。两者分开，出了问题才能分辨是"数字错了"还是"判断偏了"。所以决策层是独立脚本，输入是子图（含代表事件）+ 简报（汇总事实），输出是严格 JSON：

```json
{"priority": "高|中|低", "summary": "一句话结论",
 "risks":         [{"point": "…", "evidence": ["event_c4b0c770", "event_3f7f83b3"]}],
 "opportunities": [{"point": "…", "evidence": ["event_9253c9a0"]}],
 "actions":       [{"action": "…", "timing": "…", "reason": "…", "evidence": ["event_c4b0c770"]}]}
```

提示词里的硬约束：只能提及允许范围内的产品；证据只能用给定的事件 id；价格是后验、事件面是前瞻，不能混；市场层面只作背景；被拒过的产品只能以"可换角度再谈"的方式提及；到期只精确到月。

### 6.2 自检：不信任模型的输出

每次生成后自动检查两件事：**引用的 event_id 是否在给定集合内**、**是否提到了 13 只产品之外的标的**。第一次跑 20 份时自检报了 1 处"越界"，查下来是**自检自己的误报**（把货币代码 `CNY` 当成产品），改成只在已知的 13 只产品货架内查越界后就干净了。另外加了 `--recheck`，不调模型就能用现有产物重跑自检。

### 6.3 质量验证

**20/20 生成成功，0 失败，自检 20/20 通过。** 抽查结果：

1. **证据指向正确**——把每条结论引用的事件回溯到它在子图里属于哪个概念，**20 份里 0 处越界**（事件 id 全部在对应子图的允许集合内）：

```
[风险] 债券 / 久期风险    ← event_34ca869d（美国综合债券）、event_5a09d11b（美国长期国债）
[风险] 黄金短期承压       ← event_cf429c70（黄金）
[机会] 半导体偏正        ← event_81aece3d、event_ea32a77c（半导体）
[背景] 市场层面           ← event_dcc6e645（C001 引用）
```

2. **冷却期守住了**——C003 在 9/24 刚电话联系过（距今 5 天），决策给出的第一条行动是"**暂不主动联系，先等冷却期结束**"，时机写"当前至冷却期结束后"。

3. **被拒产品不硬推**——C018 拒过 CQQQ，决策明确写"不直接重复推荐被拒的 CQQQ"，改用她已有的 KWEB 做切入；C009 的 UUP 只在"曾被拒、可换角度"的语境里出现。

4. **两个维度没混**——20 份里有 14 份同时提到"事件面"和"近一周"，但都是分开表述，例如 C009："AGG 与 TLT 合计权重 35%，事件面净贡献 −9.015 / −7.153；**近 5 日** TLT −4.31%、AGG −1.71%"，没有把价格涨跌说成某条新闻造成的。

### 6.4 已知局限

优先级分布是 **18 高 / 2 中**。因为每个客户是**独立判断**的，这个"高 / 中 / 低"**没有横向可比性**——客户经理没法照着"18 个高优先级"去行动。要解决得做多客户统一排序，属于下一步的事。

## 8. 尚未完成与已知限制

- **推荐层还没做**：从缺口到具体动作（推哪只产品、建议金额、集中度约束）、多客户优先级排序、行动清单、offer 结果回流
- **优先级没有横向可比性**（见 6.4），需要多客户统一排序
- **覆盖率 84%**：市场层面与无落点两条通道不进产品计算
- **机器人概念只有 2 条事件**：新闻锚点缺口
- **ETF 只有前十大持仓**（80 条持仓边），这是"事件 → 产品"覆盖的主要瓶颈，需要完整持仓数据
- **客户数据是合成的**（20 个客户）；**风险等级下限表是按现有持仓倒推的**，真实业务里应由合规口径给出
- **v2 的主题词表链路**（`build_theme_vocab.py` / `apply_theme_fixes.py` / `build_theme_concept_map.py`）在 v3 已不再使用，代码与产物仍在
- **"关注过但没持有"的客户：事件入口已接上。** `news_impact.py` 现在除"直接持有"外，还输出关注未持有、offer 待定 / 已拒绝、近期卖出四类名单（第 10 节）。关注强度按行为分档（浏览 0.3 / 点击 0.5 / 搜索 0.7 / 咨询客服 1.0）、默认 30 天半衰期，只使用事件日之前的行为。还没做的：关注强度与适当性/冷却期的联合排序；现有合成数据里"关注且完全没覆盖"的样本很少，规则能跑通但还谈不上效果评估

`advisor_interactions` 是客户经理交流的**摘要**，格式为 `日期|渠道|摘要`；它目前只用于最近联系 / 冷却期，不参与主题兴趣匹配。数据里没有单独的全文交流字段，这一版也不依赖全文。

## 9. 一轮修正：事件 id、曝光度、一阶路径

### 9.1 事件 id 改成链接哈希

**问题**：事件 id 原来是事件文件里的序号（`event_001`…），而事件文件按日期排序生成。往中间插一条新新闻，它后面所有事件的 id 都平移——已经写进简报、决策里的 `evidence`（`"event_806"`）就指到别的事件上去了，而且看不出来错了。重抓一遍新闻（哪怕只多抓到一条）也会整体错位。

**改法**：`id = "event_" + sha1(新闻链接)[:8]`。

| | 好处 |
|---|---|
| 只跟新闻本身有关 | 插入新事件、重排、重跑都不变 |
| 天然去重 | 同一篇新闻在不同查询里被抓到多次，合并成同一个 id |
| 可溯源 | 链接作为 Event 节点的 `link` 属性留在图上，顺着 id 能回到原文 |

链接怎么来的：事件文件里只有 `_sample_id`（过滤后新闻的编号，如 `n0001`）。`event_ids.py` 用 `_sample_id` 回 `news_filtered_v2.json` 把链接补回来；`news_to_event_v2.py` 这一版起在抽取时直接写 `_link`，以后新数据不用再补。

安全性：`build_kg_yf.py` 建图前会自检 id 唯一性（撞哈希直接报错退出）。本轮 1031 条事件 100% 来自链接（`{'link': 1031}`），没有 fallback。

### 9.2 曝光度改成按需算

原来曝光度先全量算一遍、落成 `exposure_v3.json`，再连同 KG 一起装进库的 `event_fund_score` 表，检索层从表里查。问题有两层：

1. **它是策略输出**：权重系数（w1/w2、资产类别折扣）随时可能调，调一次就要重算全量、重灌一次库；
2. **派生数据会漂**：库里存一份分数，图里的持仓权重改了而分数没重灌，两边就悄悄不一致了。

改法：打分逻辑抽成 `exposure_v2.py` 里的 `ExposureModel`（脚本退化成命令行壳子，库表 `event_fund_score` 删掉）。检索层取子图时现算：

```
ExposureModel.from_db(con, fund_ids=[这个客户持有的产品])
```

`fund_ids` 一给，别人的产品**根本不参与计算**——"以客户为入口"是算出来的，不是筛出来的。要按事件入口看（某条新闻影响哪些产品），同一个模型传事件 id 就行。

如需一份快照排查，`python exposure_v2.py --kg src/kg/kg_yf_v3.json --out <文件>` 可以导出，但它**不是管线产物**，不再进仓库。

### 9.3 修掉一阶路径的索引 bug

规则 B（事件点名公司 → 持有该公司的产品）原来写的是 `holding[股票]`，而 `holding` 是按**产品**索引的，所以这条路径永远是空的——**所有"新闻点名了公司"的事件都没有走一阶直接暴露**，只能靠概念辐射蹭到分数。

修法：建一份反向索引 `股票 → {产品: 权重}`。影响：

| | 修前 | 修后 |
|---|---|---|
| 一阶路径命中（产品行） | 0 | **391** |
| C009 半导体净暴露 | +3.88 | **+4.24** |
| C009 人工智能净暴露 | +1.08 | **+1.14** |
| 客户侧明细行数 | 21267 | 21267（点数不变：公司类事件本来也能经概念辐射到同一批产品，变的是分数大小） |

债券那两条腿（−9.02 / −7.15）不受影响，因为公司事件落不到债券产品上。

**重构的回归校验**：把按需现算的结果和旧快照逐对（事件 × 产品）比对——2428 对分数完全一致、0 对新增、0 对消失、263 对数值变化（全部来自修好的规则 B）。也就是说"曝光度从入库改成现算"没有动口径，动的只有那个 bug。

### 9.4 顺手对齐的两处口径

- **两条取数路径的缺口措辞**：从子图取数时缺口的措辞和 strength 与文件路径不一致（旧版就存在）。已对齐，现在两份简报除 `meta.source` 外**逐字段完全相同**。
- **并列第一大持仓**：权重相同时按代码排序，避免两条路径给出不同的"第一大持仓"。

## 10. 新增：一条新闻 → 受影响的客户（事件入口）

前面所有东西都是"**以客户为入口**"：一个客户 → 他的持仓 → 哪些事件影响到他。这一节补的是反方向：

```
新闻（→ 事件）→ 受影响的产品 → 持有这些产品的客户
                 ↘ 事件命中的概念 / 资产类别 → 关注过但没持有的客户
```

输出分两类，口径不混：

- **持仓影响**：客户持有一只被这条新闻打到的产品，才算受影响。有正负号、有金额贡献（产品分数 × 持仓权重 × 实质性权重）。
- **触达线索**：和这条事件有关、但需要单独判断的客户，单独列，不并进上面的分数。分四个桶：关注过但没持有、offer 待定、offer 已拒绝、近期卖出（可重新评估）。

关注桶的规则：事件命中的概念 / 资产类别 / 产品，与 `customer_behavior` 的浏览、点击、搜索、咨询客服对上；强度按行为分档，再按 30 天半衰期衰减；只使用事件日之前的行为，避免未来数据泄漏。已经持有受影响产品的客户不重复出现在关注桶里。offer 与卖出桶按单只产品判定，所以同一个客户可以同时出现在"持有"和"待定 offer"里——这两条含义不同，前者是资产受影响，后者是该产品上有未完成的动作。

offer 是"向客户推荐某只产品"的记录：`ticker` 是被推荐的产品，`reason` 是推荐理由，`status` 是接受 / 待定 / 已拒绝。理由里出现"替代个股""替代部分存款"这类说法，是资金来源或组合层面的解释，不改变 offer 本身的方向。因此不从理由推断动作：**待定 = 推荐尚待决策；已拒绝 = 不再重复推同一只产品**。已持有产品上的 offer 也不再跳过，含义是"在现有持仓上继续加配"。

客户仍然不进图——产品 / 概念到客户这一步是拿 `customer_holding`、`customer_behavior`、`customer_offer`、`customer_trade` 四张表 join 出来的。

### 10.1 三种入口

| 入口 | 用法 | 说明 |
|---|---|---|
| 事件已经在 KG 里 | `python news_impact.py --event event_5a09d11b` | 不调模型、不联网，秒出 |
| 一条新新闻 | `python news_impact.py --title "…" --date 2026-09-30 --publisher Reuters --url https://… --api_key sk-…` | 走**同一条管线**，只是单条：判 scope → 抽事件 → 标概念×驱动（2 次模型调用），然后出名单 |
| 一批新新闻 | `python news_impact.py --news <新闻文件.json> --api_key sk-…` | 文件里几条就处理几条；抽取逐条调模型、概念标注每 15 条一批，**图与库只重建一次** |

新新闻**默认直接入库**：事件落进 `_yf_data/events_v3_extra.json`，随后重建图与库——这两步是确定性的、约 1.5 秒、不吃模型，所以"加一条新闻"就是一条命令。想先看影响再决定，加 `--preview`，那就一个文件都不写（影响照样算得出来，见 10.4 的一致性校验）。

批量时的两个护栏：条数超过 20 会先拦一下（要跑得显式 `--limit N` 或 `--yes`，免得手滑把一个上千条的语料丢进来）；**已经加过的新闻（链接相同）按 id 去重**，重复加不会变成两条——事件 id 是链接哈希，所以哪怕模型这次标出来的驱动不一样，id 还是同一个，建图时会跳过。

增量文件跟批量语料分开放，是全量重跑也不会丢的原因；而**插入新事件不会让已有事件的 id 平移**，靠的正是第 9.1 节的链接哈希——这也是当初把它改掉的实际收益。

### 10.2 输出长什么样

以库里的一条真实事件为例（`event_5a09d11b`，"TLT 从高点腰斩"）：

```
事件 event_5a09d11b | 2026-09-27 | negative | MarketEvents | 驱动 Market Flow
  概念：us_long_treasury   通道：concept   scope：entity

受影响的产品 2 只：
  TLT    -1.4500  direct_product + anchor_fund + same_asset_class(FixedIncome)
  AGG    -0.1500  same_asset_class(FixedIncome)

受影响客户 16 位（只算持有上述产品的）：
  C001  陈建国  C2  贡献 -0.4185   TLT 45%→-0.3915；AGG 30%→-0.0270
  C017  黄伟民  C2  贡献 -0.2970   TLT 30%→-0.2610；AGG 40%→-0.0360
  ...
```

看得到三件事：**哪些产品被打到**（含打分路径，能解释为什么）、**哪些客户持有**、**每个客户被影响多少**（贡献 = 产品分数 × 持仓权重 × 实质性权重，和客户简报里是同一套口径）。

同一份输出后面还有非持仓客户。以库里一条油价事件（`event_3a9c763e`）为例：

```
受影响的产品 1 只：
  USO    +0.3000  anchor_fund(concept_oil)

受影响客户 2 位（只算持有上述产品的）：
  C011 / C009

关注过但没持有 1 位：
  C020  关注度 0.653   2026-09-25 搜索了「原油」（勿推 USO）

offer 已拒绝 1 位：
  C020  USO  已拒绝（不主动再推） 16 天  油价上行对冲

近期卖出、可重新评估 2 位（120 天内）：
  C018  USO  41 天前卖出
  C005  USO  68 天前卖出
```

同一个人可以既是"关注了原油"又是"拒绝过 USO"：前者说明这个方向值得聊，后者说明不要再用 USO 去推；关注记录上的"勿推 USO"就是这两条信息的交叉。三个阈值都有命令行参数：`--interest-half-life`（默认 30 天）、`--min-interest`（默认 0.15）、`--sold-days`（默认 120 天）。

### 10.3 与"以客户为入口"的关系

两条路用的是同一个打分模块（`exposure_v2.ExposureModel`）和同一套口径参数，只是一个从客户出发、一个从事件出发。事件通道是 `market` / `gap` 且没有落到具体产品和概念时，持仓名单会为空；关注桶只按事件带的概念 / 资产类别匹配，offer / 卖出桶只按被打到的产品匹配，也不会凭空产生名单——这是预期结果，不是出错。

### 10.4 一次实测（增量入库）

拿一条编的新闻（Nvidia 因美国收紧 AI 芯片出口管制预警 50 亿美元损失，2026-09-30）走过一遍完整链路，测完已从图里清掉。记录几个数：

| 检查项 | 结果 |
|---|---|
| 图规模 | 1316 节点 / 2590 边 → **1317 / 2593**（只多 1 个事件节点 + 3 条边：`HAS_THEME`×2、`AFFECTS→stock_NVDA`） |
| 原有 1031 条事件 | id **一条没变**（插入不影响已有事件） |
| 受影响产品 / 客户 | 6 只（SMH −0.81、SOXX −0.61、AIQ −0.43、XLK −0.32、QQQ −0.23、BOTZ −0.15）／ 19 位客户 |
| 落库那次输出 vs 事后按 id 再查 | 完全一致 |
| 预览（直接给概念算）vs 入图（走图上的边算） | 6 只产品分数逐个相同 |

也就是说"先预览、再决定入不入库"这两步的数不会对不上；重建图与库约 1.5 秒，不吃模型。

## 11. 客户级聚合：从事件名单到客户清单

第 10 节的输出是「事件 → 一批客户」。实际使用时还需要反过来看：「这个客户当前有什么相关事件和信号」。

新增：

- `customer_signals.py`：把事件→产品、产品→直接持有客户、关注/offer/卖出抽成可复用模块；
- `customer_actions.py`：按时间窗口把事件聚到客户，输出持仓影响、关联信号和相对优先级。

```bash
python customer_actions.py --days 7
python customer_actions.py --customer C006 --days 7
python customer_actions.py --out _yf_data/customer_actions.json
```

聚合规则：

- 默认窗口为参考日期前 7 天；参考日期取 `meta.price_as_of`，也可用 `--date` 指定；
- 同一天、同概念集合、同方向的多条新闻先归并，保留贡献最大的一条作代表；
- 持仓影响按「产品分数 × 持仓权重 × 实质性权重」计算；
- offer 和近期卖出按产品去重，保留最近一条；
- 优先级是本次运行内的相对排序（前 25% 高、接下来 35% 中、其余低），不是绝对风险等级。

C006 示例：

```text
[高] C006 赵雪  优先级 1.2494
  持仓影响 276 条 → 归并 177 组（展示 5），最大单条 0.7530
    2026-09-28 Nvidia 回购新闻（同类 5 条）
      SMH 30%→+0.3127；SOXX 25%→+0.2165；QQQ 15%→+0.1092
```

全量 20 个客户、7 天窗口跑完约 3 秒，不调用模型。

目前的优先级只用于展示排序，还没有把适当性、集中度、冷却期、每日触达上限合成统一策略；这些是后续推荐层的工作。
